# The method

This document explains the design and where each piece comes from. If you
just want to set it up, read [`getting-started.md`](getting-started.md)
instead.

## The problem

AI agents are good at working inside a folder and bad at remembering it. Every
session starts from nothing. Given a bare directory, an agent will guess your
conventions from the filenames and be confidently wrong about what state the
work is in.

The usual reactions are to write longer prompts or to paste context by hand at
the start of every session. Both are the same mistake in different clothes:
they treat context as something you carry into the session, when it should be
something the session finds already there.

The alternative is to write the context down, in plain text, in the folder
where the work already lives. The agent reads it because it is there. You read
it too, which turns out to matter more than expected.

## The structure

### Workspaces

Split work by role or area of responsibility, one workspace each. A researcher
might have research, teaching, and department administration. A consultant
might have one per client plus one for the business itself. The test is not
topic but reporting line: if the work has different rules, different people
and different confidentiality, it is a different workspace.

Keep personal life in a separate tree entirely. Not a subfolder.

Why split at all, rather than one big folder: rules are per workspace and they
should be short. An `AGENTS.md` that tries to cover teaching and research at
once ends up saying "it depends" a lot, which helps nobody.

### Units, and the three-file contract

Inside a workspace, every unit of work is a folder: a project, a course, a
client engagement, a person you supervise, a standing responsibility. Each one
holds three files.

**`README.md`** answers what this is. Purpose, who is involved, and where the
real thing lives if it is not here. This last point does a lot of work: if the
manuscript is in Overleaf and the code is in a git repository, the README says
so, and nothing in the folder pretends to be canonical. It changes rarely.

**`STATUS.md`** answers where things are right now. State in one line, the
single next action, pending items with dates, and what is blocked and on whom.
It is overwritten, never appended to. It should fit on one screen; if it does
not, the unit is probably two units.

**`LOG.md`** answers what was decided and why. Dated entries, newest first,
two to four lines each. Append-only. Old entries are never edited, and a
decision that reverses an earlier one says so explicitly.

The split between the three is the whole idea, and it maps onto three
different rates of change. Confusing them is the most common way this
degrades: a `README.md` that accumulates status, a `STATUS.md` that grows a
history section, a `LOG.md` someone tidies up.

A worked example is in [`../examples/`](../examples/).

### Instructions for agents

`AGENTS.md` at the workspace root holds the rules: how the workspace is
organized, what the conventions are, what is confidential, what an agent must
never do without asking. This is the file that turns a folder into a place an
agent can work.

Claude Code does not read `AGENTS.md` directly, so put a `CLAUDE.md` beside it
that does nothing but import the canonical file (`@AGENTS.md`). Every other
agent reads that file itself, and there is exactly one copy of the rules.

Individual units can have their own `AGENTS.md`, but only when they have rules
of their own. A unit-level file that repeats the workspace rules is a
liability, because the two copies will disagree eventually.

### Skills

A skill is a folder with a `SKILL.md` file: YAML frontmatter with a name and a
description, then Markdown instructions. Agents read the description at
startup and load the body only when the task matches.

This is where repeatable procedure goes. "Create a new project folder from the
right template" and "close the session by updating STATUS and LOG" are
procedures you would otherwise retype, or worse, rely on the agent to
improvise.

The four that operate the structure itself are described below, and shipped in
[`../skills/`](../skills/).

### Derived views, never a second list

The board of everything pending across workspaces is generated by reading the
`STATUS.md` files. It is not a file anyone maintains.

This is worth being strict about. The moment a global task list exists as its
own document, it becomes a second source of truth, and it will diverge from
the units within a fortnight. Anything you want to see across workspaces
should be computed on demand from the files.

## Where this comes from

Almost nothing here is original. Each piece copies an open standard or an
established practice, which is the point: the parts are already documented,
already supported by tools, and already debugged by more people than would
ever use a bespoke system.

**Plain text over applications.** This is the "file over app" argument from
Steph Ango, CEO of Obsidian (https://stephango.com/file-over-app). Files
outlive the applications that read them, so durable knowledge should be stored
in formats that any future tool can open. For agents there is a second reason:
reading, searching and writing files is the operation they perform most
reliably.

**`AGENTS.md` is an open standard** (https://agents.md). It began as a README
for coding agents, backed by OpenAI, Google, Cursor, Amp and Factory, and is
now stewarded by the Agentic AI Foundation under the Linux Foundation. More
than twenty tools read it and over 60,000 open-source projects ship one. The
`CLAUDE.md` bridge uses the import syntax documented in the Claude Code memory
guide (https://code.claude.com/docs/en/memory).

**Skills are an open standard too.** Anthropic introduced the format in
October 2025
(https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
around the principle of progressive disclosure: the agent holds only each
skill's name and description in context, and loads the full instructions when
it decides the skill applies. The specification was released openly in
December 2025 (https://agentskills.io) and adopted within days by Codex
(https://learn.chatgpt.com/docs/build-skills) and VS Code, among others. This
is why the same skill folder works across agents without modification.

**The three-file contract is a memory bank.** The pattern of giving an agent
persistent memory as structured Markdown inside the project, read at the start
of a session and updated at the end, was popularized by the Cline community
(https://docs.cline.bot/features/memory-bank). Anthropic's guidance on context
engineering makes the same argument from the other direction
(https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents):
model context is a finite resource, so durable knowledge belongs outside it,
retrieved when needed.

**`LOG.md` is an Architecture Decision Record.** The practice comes from
software engineering, specifically Michael Nygard's 2011 note on documenting
architecture decisions
(https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions):
record each decision with its date, its context and its reasoning, in a
register that only ever grows. It supplies exactly what an overwritten
`STATUS.md` structurally cannot, which is why both files exist.

**Pending work comes from GTD and PARA.** From Getting Things Done (David
Allen, https://gettingthingsdone.com): a single trusted system outside your
head, and an explicit next action rather than a vague project name. Every
`STATUS.md` carries one. GTD's weekly review is the generated board. From PARA
(Tiago Forte, https://fortelabs.com/blog/para/): the split between projects
that end, areas that do not, resources, and archive. A workspace organized by
kind of work, with a separate `areas/` for standing responsibilities and an
`archive/` that is searchable rather than curated, is PARA with different
labels.

## The core skills

Four skills operate the structure. Everything else you build will be domain
work sitting on top.

**`new-unit`** creates a unit from the right template. Its value is not saving
keystrokes, it is that every unit starts with the contract already in place.
Units created by hand are the ones that end up missing a `LOG.md`.

**`session-log`** closes a session: overwrite the touched `STATUS.md`, append a
dated entry to the `LOG.md`. This is the write-back half of the loop and the
single point of failure of the whole method. A workspace where sessions are
not closed decays into a directory of stale files within about a month.

**`workspace-overview`** derives the pending-work board by scanning
`STATUS.md` files across workspaces. Read-only by design.

**`audit-workspace`** checks units against the contract (missing files,
unfilled placeholders, `STATUS.md` files that have not moved in months) and
surveys what is not activated yet, including folders holding work with no
contract at all. The check is for a settled workspace; the survey is for one
being adopted over folders that already exist.

Three more are worth building once you have adopted this and hit their
absence. None ships here, because the right shape depends on your setup. An
**activate** skill that drafts the contract for a folder that already holds
material, which is the repetitive half of adoption; note that it has to be
additive only and honest about what it cannot know, since a confidently wrong
`STATUS.md` is worse than none. An **archive** skill for lifecycle moves,
since promoting or retiring a unit is a multi-step operation you do not want
improvised on storage without version control. And an **inbox triage** skill,
if you keep an `inbox/` folder and it stops trending toward empty.

## Practical constraints

**Cloud storage is not version control.** Google Drive, Dropbox and OneDrive
give you sync, not history. There is no meaningful undo for a bulk move. If
your workspaces live on one of these, the working rules are: copy before
moving, archive instead of deleting, and never let an agent perform a bulk
operation without confirming first.

**Code does not go in the workspace.** Git and cloud sync interact badly.
Repositories live outside the synced tree, and the unit's `README.md` points
at them. This is the "canonical source lives elsewhere" rule doing its job.

**Symlinks do not survive cloud sync**, which affects how skills are shared.
Cross-workspace skills can live in one git repository symlinked into each
agent's skills directory, since those directories are local. Skills that live
inside a synced workspace have to be real folders.

**Not every agent auto-discovers local skills.** Claude Code loads skills from
`.claude/skills/` automatically; other agents do not necessarily. The
workaround is a `## Skills` section in the workspace `AGENTS.md` listing each
skill with its path and its trigger, written so that an agent that cannot
discover the skill can still be told to read and follow it. Every agent reads
`AGENTS.md`, so it works as the bridge.

## Known weaknesses

Stated plainly, since you would find them anyway.

**It depends on closing sessions.** `session-log` exists and works, but
something has to trigger it. A hurried session that ends without it leaves
`STATUS.md` lying, which is worse than having no `STATUS.md`, because the
agent believes it.

**Adoption is slow and partial by nature.** Migrating folders is fast; writing
a real `README.md` and `STATUS.md` for each one is not, because it requires
actually deciding what the unit is and what state it is in. Expect a long
period where some units are activated and most are merely moved. That is not a
failure state, but it does mean the generated board is incomplete, and the
board should say so rather than imply silence means nothing is pending.
[`adopting-existing-work.md`](adopting-existing-work.md) covers this phase in
detail, since it is where most of the real work happens.

**Templates invite filler.** A template with placeholders can be satisfied
without being filled in, and a `STATUS.md` reading "TODO: describe this" is
worse than an absent file. This is what the audit skill is for.

**Skills duplicated across workspaces drift.** Two copies of `session-log`
adapted to different workspaces will diverge, and eventually one of them is
just wrong. Either keep one generic version and parameterize it, or accept the
divergence deliberately and write down why.

**The contract is not free.** Three files per unit is real overhead, and for
short-lived units it is not worth it. Units that live for a week and have one
piece of state deserve a single file, not the full contract. Applying it
uniformly because it is the rule is how a system starts producing paperwork
instead of context.
